## 正式签发拟执行范围

正式入口已选定为 `134.175.137.18`。新增一次性签发候选 `backend/tools/travel_tls_issue.py`。它在本机默认只输出审阅状态。将来经正式签发授权后，Linux 上以 root 运行且显式选择 `--issue --use-contact` 或 `--issue --no-contact`。前者从原机 root 管理、权限为 `0600` 的 `/etc/travel-tls/acme-contact` 读取运维邮箱，后者要求已同意无邮箱注册。历史测试签发授权已用完。

- 先以 ubuntu 用户核对原 80 端口、webroot、挂载和共享 nginx 配置，再核对已安装的 Certbot。首签使用包含 webroot 权限竞态修复的 5.10.0 或更新版本。[Certbot 5.10.0 发布说明](https://github.com/certbot/certbot/releases/tag/v5.10.0)
- 有效执行会在专用目录落盘 `first-order.jsonl`，随后调用一次 `certonly`。若连接中断、Certbot 超时或证书核验失败，保留该回执和私有状态便于核对。继续前先按同一次记录查清是否已签发。
- 验收核对正式 CA 的续期元数据、系统信任链、唯一 IP SAN、短有效期和私钥匹配，并确认挑战文件清理、共享 webroot 复查通过。脚本和依赖由 root 管理，六份运行文件同目录放在 `/usr/local/libexec`，以回执中 SHA-256 为准。实际签发、证书装载与公网 TLS 验收分别核对。[首签候选回执](verification/budget-ip-first-production-order-candidate-2026-11-19.json)

仅在明确授权后，在已核对的原机创建一份新的专用状态。`/etc/travel-tls/acme`、`/var/lib/travel-tls/work`、`/var/log/travel-tls` 由 root 管理、目录为 `0700`；空白 `/etc/travel-tls/empty.ini` 为 `0600`。如有已有状态或路径指向不清，停止并审阅。使用本机已有的 Certbot 5.10.0，沿用已实测通的 80 端口和 `/opt/continew/web`。公共 webroot 仅存放 HTTP 验证 token，不放签发账户、私钥或签发日志。证书和密钥保留在服务器，`privkey` 为 root 可读写，不在回执中导出。

下方保留原命令供核对参数。实际执行首签时使用带本地记录和复核的入口。`TRAVEL_ACME_CONTACT` 如采用运维地址，由操作者在原机设置；不会写入本仓库或验收回执。`--required-profile shortlived` 将默认签发配置回退视为失败。`certonly` 只负责获取证书。[Certbot 选项](https://eff-certbot.readthedocs.io/en/stable/man/certbot.html)

```bash
/snap/bin/certbot certonly --server https://acme-v02.api.letsencrypt.org/directory \
  --required-profile shortlived --webroot --webroot-path /opt/continew/web \
  --ip-address 134.175.137.18 --cert-name travel-ip-public \
  --non-interactive --agree-tos --email "$TRAVEL_ACME_CONTACT" --no-directory-hooks \
  --config /etc/travel-tls/empty.ini --config-dir /etc/travel-tls/acme \
  --work-dir /var/lib/travel-tls/work --logs-dir /var/log/travel-tls
```

正式授权只覆盖签发时，仍不配置公网服务。签发后先独立核对正式 CA、唯一 IP SAN、短有效期、证书链完整、证书与私钥配对、账号/证书文件权限、挑战目录清理和共享配置不变；任何一项失败都保留受限证据并停止，不自动追加订单。短有效期意味着签发宜接近已批准的 443 准备时间，避免签完一直闲置。

## 续期、装载和告警

- `deploy/travel-tls/travel-ip-renew.*` 是未安装的 systemd 候选：每天四次检查是否该续期，不强制签发；只处理独立状态中的 `travel-ip-public`，预检拒绝测试 CA、其他 webroot、额外安装器和已配的命令钩子。续期后检查保存的链、私钥匹配和到期风险。初次签发与定时任务均不接管 Snap 现有的全局状态。正式启用前，确认计划的任务不会和既有任务重复管理同一 lineage。
- 将 nginx 使用的证书副本与 ACME 账户目录分开。下一阶段需验证一个仅影响独立 nginx 的装载路径：从已核对的同一代证书和私钥生成新的受限目录，保留上一代，序列化换代和加载，先 `nginx -t` 再加载，最终以 TLS 刚送出的指纹核对。如果加载或核对失败，保持已知可用代；无可用代时保持维护并告警。不能仅凭 Certbot 退出 0 判断续期已对网站生效。**当前定时续期候选没有安装证书或加载 nginx 的钩子，须通过这一步后才允许启用。** [Certbot 续期钩子与退出码](https://eff-certbot.readthedocs.io/en/stable/using.html#renewing-certificates)
- `travel-ip-watch.*` 是每小时的公网证书检查候选：严格验证 IP、证书链、短周期以及实际送出的叶证书是否等于最新保存版本。剩余不超过 72 小时记录警告、不超过 36 小时记录严重；连接、验证或指纹不匹配也会给非成功状态。守护任务只输出脱敏 JSON 到系统日志，**还没有接入送达人的告警渠道**。正式启用前需明确值守人和通知渠道，在外部网络也完成一次 TLS/到期告警送达验收，避免原机宕机时本机日志不可见。
