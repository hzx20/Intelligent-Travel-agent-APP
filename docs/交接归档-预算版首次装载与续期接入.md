## 本次改动

- `travel_tls_edge.py` 默认输出审阅信息。`prepare-first --apply` 从正式 Certbot 证书库读取同代证书链及私钥，核对签发配置、系统信任链、唯一公网 IP SAN、证书有效期与密钥配对。它仅在尚无当前证书时写入独立受限目录。随后由单独批准的部署步骤启动维护代理。
- `verify-first` 查验未发布端口的维护代理，运行 nginx 语法检查，并在容器内对旅行入口做两次受信任的 HTTPS 握手。两次均须返回 503 并送出同一预期叶证书。首装通过表示维护代理确实加载了所选证书，`public_verified=false`。
- `reconcile --apply` 仅操作登记的独立旅行代理。每次执行前核对完整容器 ID、镜像 ID、运行身份、私网、IPv4 443 发布、挂载和宿主/容器两侧的 nginx 配置哈希。当前叶证书可确认时才换代；若新证书已在使用，则跳过重载。换代失败时尝试恢复并复核旧证书；失败仍通过非零退出码反映在 systemd 状态中。原续期单元保留，新增的 drop-in 示例在保存证书配对检查后调用该入口。[此前同镜像换代演练](交接归档-预算版证书装载与回退.md)

## 恢复所需信息

1. 先核对[本轮机器回执](verification/budget-ip-tls-edge-handoff-2026-11-19.json)、[正式签发与续期审阅](交接归档-预算版正式证书与续期审阅.md)和[代理信任验收](交接归档-预算版代理信任验收.md)。本机审阅命令为 `python -I -B backend/tools/travel_tls_edge.py`。实际 Linux 运行时，三个 `travel_tls_{check,rotate,edge}.py` 放在同一 root 管理目录 `/usr/local/libexec`，供示例单元调用。
2. 获得正式签发和部署授权后再绑定现场实例。准备 `/etc/travel-tls` 与 `/etc/travel-tls/edge`（root，`0700`），`/etc/travel-tls/edge-nginx.conf` 和 `/etc/travel-tls/edge-target.json`（root，`0600`）。目标 JSON 只含 `id`（完整 64 字符十六进制容器 ID）、`image`（带 `sha256:` 的镜像 ID）、`network`（已确认的专用网桥名）、`ip`（实际保留的桥内 IPv4）、`config_sha256`（回执中的候选哈希）。现场目标尚未登记。
3. 独立容器名为 `travel-https-edge`，标签为 `travel.edge.role=travel-ip-https`，root 运行已核对的 nginx master，根文件系统只读，`/tmp` 为专用 tmpfs。只读绑定 `edge-nginx.conf` 到 `/etc/nginx/nginx.conf`，绑定 `edge` 目录到 `/etc/nginx/travel-tls`；`current` 是代际选择指针。正常模式另把 `/opt/continew/web/travel` 只读挂到 `/usr/share/nginx/html/travel`。静态目录或配置如果通过替换 inode 发布，须随下次切换重建挂载并重新核对。配置或容器变更时先暂停续期加载，复核运行实例及最新候选，再重新登记完整 ID。
4. 维护代理首装核验通过后，在批准的切换窗口复核实际 443、外部信任链、真实代理私网来源与 8000 的入站边界。公开、重建容器或更换配置须重做身份和挂载核对。正式代理与当前叶证书经外部验证后，再启用示例 drop-in；随后实测续期状态及外部已送出证书的一致性。回退失败或送出证书与磁盘指针不一致时，保留现有证据和证书代，按维护流程恢复后再重启自动加载。告警接收渠道和接收人仍待确认。
