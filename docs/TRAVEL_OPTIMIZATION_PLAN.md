# 智能旅行规划 Agent 全栈优化与质量计划

审阅基线为 `55efbf4`。工作分工沿用 [三端执行计划](../PLAN.md)。本文的验收值为首轮目标，进入开发时以同一提交、设备和测试数据复测基线。

## 1. 目标和实施顺序

首先打通「选择目的地或输入需求 → 生成并查看行程 → 保存为可编辑旅行 → 再次打开」。其次统一地图、预算和来源的表达，完善断线、供应商故障和多人编辑时的恢复体验。实施沿用 Vue 3、FastAPI、LangGraph 和 SQLite，运行与发布沿用 `/travel/` 路径及现有发布工具。架构评审以实际代码、CI 与部署文档为依据。[项目入口](../README.md) · [路由](../frontend/src/router/index.js) · [发布手册](../deploy/RELEASE_RUNBOOK.md)

| 优先级 | 交付 | 通过条件 |
| --- | --- | --- |
| P0 · 基线和防回归 | 测试入口、核心用例清单、风险登记、桌面与移动端基线。 | 用例能复跑，记录提交、环境、失败、跳过项及原因。数据丢失、重复写入和权限隔离的风险有明确验收用例。 |
| P1 · 入口与生成 | 旅行工作台、灵感页、规划流程及结果页改版。 | 新访客可从首页找到 AI 规划，回访用户可直接继续旅行。断线、取消、失败和完成均有明确后续动作。 |
| P1 · 编辑与集成 | 统一行程编辑、地图与状态反馈，逐步完善供应商降级和预算标注。 | 原有旅行可打开，版本冲突保留输入，离线与浏览器回归通过。 |
| P2 · 持续优化 | 用真实设备试用、快照回归、检索评测和性能复盘完善细节。 | 依据试用和监控选下一批任务，记录改进前后差异。 |

## 2. 前端重设计

### 视觉和布局

延续自然绿风格，在 `frontend/src/assets/main.css` 统一品牌主色 `#1A6E50`、背景 `#F7F6F1`、正文 `#20342C`。用暖橙突出少数行动，用语义色配合文字与图标展示成功、警告和失败。正文从 14 px 调至 16 px 左右，采用统一的标题、间距、圆角、阴影和键盘焦点样式。梳理目前全局变量与页面内重复配色，优先统一按钮、行程卡、提示条、空状态、弹窗和筛选控件。用同一组图标替换导航和操作区的装饰性 emoji，保留操作文字。主 CTA 保持单一，底部导航预留安全区。[现有全局样式](../frontend/src/assets/main.css) · [导航](../frontend/src/App.vue)

| 页面 | 当前代码观察 | 改版方向 |
| --- | --- | --- |
| `/` 旅行首页 | 根路由实际是旅行工作台。桌面欢迎区最小高度为 340 px，首屏包含欢迎区、新建入口和旅行列表。 | 已有旅行时把「继续上次旅行」与最近列表移到首屏。新访客只突出「AI 帮我规划」，「手动新建」作为次操作。账号旅行、本机旅行、AI 历史用状态和保存位置明确区分。 |
| `/inspiration` 灵感及景点 | 灵感页现有规划表单、热门目的地、推荐和攻略入口。目的地卡片按位置切换固定渐变。 | 首屏用一张有授权的目的地实景图和单行规划入口，下方保留少量目的地与可操作的收藏或预填按钮。照片只放在有内容价值的区域，按尺寸输出 AVIF/WebP，失败时保留等高占位。 |

## 3. 业务和交互优化

| 问题或待确认点 | 改进思路 | 验收 |
| --- | --- | --- |
| 旅行首页、灵感表单、独立规划页分别承担任务入口，AI 生成和已有方案转旅行分布在不同页面。 | 把「开始规划」「保存为旅行」「继续编辑」连成一条路径。目的地预填与返回导航保留已输入内容。结果区明确标出方案已生成、账号历史已保存、可编辑旅行已创建等状态。 | 新访客从首页发起，历史方案可以找到或转换，可编辑版本可回读，重复操作只得到一份对应旅行。 |
| 已有处理提交结果待核对、取消、轮询失败和 30 分钟任务留存。用户仍需理解多个状态及各自重试入口。 | 在现有可靠提交和轮询基础上，将页面文案归并为下表的用户状态。保留 `request_id`、请求快照及账号或游客归属，核对结果后决定继续。拆分视图时按任务状态、地图渲染、历史管理分别提取职责。 | 刷新、切页、丢响应、重连和切换账号均能看到契合当前状态的动作。旧响应不能覆盖新会话。 |
| 本机旅行与账号旅行已有手动复制和保留原件的语义。失去连接后，用户容易把待核对理解为没保存。 | 卡片标明保存位置。复制前说明包含的数据和原件去向，完成后直接给账号版本入口。遇到结果未知，先回读原请求，保持草稿。 | 模拟复制响应丢失再刷新，能找回同一份副本，本机原件保留，其他账号看不到该操作。 |
| 旅行详情同时处理路由切换、草稿保护、共享版本和子面板。 | 把脏状态、服务端版本及冲突决策集中到现有草稿与会话逻辑。对 `409` 显示服务端已更新，保留本地编辑并提供比较、复制或加载最新版。撤权后收起受限内容并返回安全入口。 | 双标签互相编辑可复现冲突，较旧版本不能静默覆盖。分享撤销与账号切换后，旧页面和旧请求均按权限处理。 |
| 生成结果包括资料引用、地图核实、估算费用和天气，但这些信息的置信度及更新时间不同。 | 行程卡分别标注「地点已核实」「顺序示意」「费用估算」「外部数据暂缺」。列表可独立使用。来源链接展示到具体条目或固定修订，供应商错误按超时、配额耗尽或无结果给出可执行提示。 | 地图失败仍能浏览列表。RAG 无资料仍完成离线模拟生成。未知价格显示待确认，预算可以追溯到明细。 |

| 规划状态 | 主要反馈与动作 |
| --- | --- |
| 待补充 | 显示已确认的城市、天数与偏好，聚焦下一项必填信息。 |
| 提交待核对或重连 | 保留输入，说明任务可能在后台运行，可继续核对原提交。 |
| 生成中 | 显示已完成的阶段、用时以及停止入口。阶段进度来自任务回执。 |
| 完成、失败或取消 | 完成时查看结果和保存为旅行。失败时说明原因并复用输入。取消时等服务端确认后结束等待。 |

代码依据包括现有的 [可靠创建及轮询](../backend/app/routers/planner.py)、[任务生命周期](../backend/app/services/plan_jobs.py)、[规划会话](../frontend/src/store/planSession.js)、[本机旅行](../frontend/src/store/guestTrips.js)、[检索与降级](RAG.md) 和 [供应商约束](travel-data-suppliers.md)。这些是源码审阅发现和待验证风险。涉及真实用户是否会误解、生产延迟与故障率，由实机走查和运行数据验证。

## 4. 测试流程与质量门槛

现有 GitHub CI 运行后端离线 pytest 和 `/travel/` 前端构建。仓库另有前端 `node:test`、多套 Playwright 配置、隔离后端和临时 SQLite 夹具。优先把已存在的检查接成一条复跑路径。模型与供应商的实调采用单独的测试环境和额度。[CI](../.github/workflows/ci.yml) · [前端用例](../frontend/test) · [浏览器配置](../frontend/package.json) · [后端夹具](../backend/tests/conftest.py)

1. **编写。** 需求卡写明用例 ID、业务风险、角色与数据、操作、预期界面、API 或数据库断言、运行层级和证据。每条关键路径覆盖成功、失败恢复和权限或重试边界。优先用最小可稳定复现的层级。
2. **评审。** WorkBuddy 提交用例和执行结果。另一窗口核对契约与预期。Muse 清点高风险场景，抽查断言能抓到重复写入、静默覆盖或越权，并在 Issue 记录缺项。Codex 决定评审通过及回归范围。
3. **执行。** 本地先跑受影响的测试层。PR 每次更新跑后端离线回归、前端单测、构建与所选关键浏览器用例。主分支定期运行更完整的套件。发布候选另做旧库升级、移动真机和生产环境适用的冒烟，保存对应提交。
4. **判定。** 测试报告记录提交与产物、环境、用例总数、失败、跳过、耗时和证据。失败先分类为产品、用例、环境或已知基线差异。重跑保留初次记录，间歇失败有 Issue、负责人和退出条件。关键用例缺证据、失败或被跳过均为待验收。未关闭的 P0/P1 风险阻塞相关发布。P2 例外由 Codex 记录影响范围、处理人、到期日和恢复措施。

### 首批关键用例

| ID | 条件与动作 | 核心断言 | 层级 |
| --- | --- | --- | --- |
| TR-01 | 游客从首页或灵感页带目的地进入规划，完成澄清。 | 预填正确，刷新可按当前会话恢复。生成的天数和已确认条件一致。 | Playwright ＋后端 |
| TR-02 | 创建成功后截断响应，刷新并核对原提交。 | 原请求标识有效，返回同一任务，数据库只有一条有效创建记录。 | pytest ＋ Playwright |
| TR-03 | 任务挂起、断线、轮询失败或取消，同时模拟迟到响应。 | 状态正确，已取消的任务不会重新显示为完成。 | pytest ＋ Playwright |
| TR-04 | 游客新建旅行、刷新、登录复制，模拟丢响应再打开。 | 本机原件、账号副本和保存位置准确，副本数量正确。 | Playwright ＋ API |
| TR-05 | 两个编辑端提交不同版本，刷新另一个端。 | 旧更新被拒，输入可找回，服务端当前内容可回读。 | pytest ＋ Playwright |
| TR-06 | 只读分享、未接受邀请、撤销权限、切换账号。 | 访问和写入权限正确，私有预订和费用不会出现在只读分享。 | pytest ＋ Playwright |
| TR-07 | 模拟地图、模型检索、天气或其他供应商的失败及空结果。 | 核心列表可用，降级提示明确，无虚构报价，无失控重试。 | 单元、API、浏览器 |
| TR-08 | 使用合成旧库升级，核对旅行、预订、足迹和外键。 | 数据可回读，备份和回退候选可用。 | 部署隔离验收 |
| TR-09 | 320/390 px 触屏和 1280 px 桌面完成规划与编辑，键盘遍历。 | 无横向溢出、遮挡、焦点丢失。关键操作有名称，错误可感知。 | Playwright ＋真机 |
| TR-10 | 固定检索留出集，加入儿童、少走路、同名地点与价格边界。 | 记录 Recall@3、降级率和耗时。抽查引用与实际建议一致，估算与已知费用区分。 | 检索评测＋人工抽查 |

### 工具与提效

仓库根目录运行 [统一 QA 脚本](../scripts/travel_quality.py)。先按现有 CI 的环境安装 `backend/requirements.txt` 和 `frontend` 锁定依赖，激活 Python 虚拟环境。本地执行浏览器套件需准备已有配置使用的 Edge，或通过 `TRAVEL_E2E_CHANNEL` 选择已安装的兼容渠道。

```sh
python scripts/travel_quality.py backend
python scripts/travel_quality.py frontend
python scripts/travel_quality.py browser
python scripts/travel_quality.py all --report-dir ../travel-qa-run-01
```

`backend` 复用现有 CI 的离线筛选，`frontend` 跑 `node:test` 和 `build:travel`，`browser` 串行复跑旅行首页、可靠规划创建与旅行工作区的现有桌面和移动端测试，避免隔离服务端口冲突。脚本采用空的测试配置文件、占位模型配置及既有隔离夹具，输出逐项日志、JUnit、Playwright 失败附件和 `summary.json`。任一检查失败、预期报告缺失或整组用例未执行时返回失败。省略 `--report-dir` 时使用新的临时目录。

下一步将统一脚本接入 CI，上传结果、截图和失败 trace，按改动目录选跑受影响的浏览器套件。扩大并行前先参数化隔离端口和 SQLite 路径。固定合成数据和网络失败夹具，把慢速真实调用移到获授权的候选验证。视觉快照按桌面和移动端分组，差异由设计和测试共同确认。检索评测沿用既有留出集并纳入新场景。按每周的中位反馈时间、间歇失败率及核心用例覆盖检查提效，首轮以实际运行记录建立基线。[现有检索评测](RAG.md)

## 5. 风险、监测和上线

| 风险 | 初始级别 | 控制与责任方 |
| --- | --- | --- |
| 重复提交、草稿丢失、旧版本覆盖 | P0 | WorkBuddy 复用请求标识和版本检查。Muse 对照 TR-02、04、05 看回执。Codex 对未解决的数据风险停止相关发布。 |
| 私有行程、凭证、预订和费用泄露 | P0 | 后端用例覆盖访客、所有者、受邀者和撤权。公开报告使用合成数据并脱敏。Muse 核对 TR-06 和报告内容。 |
| SQLite 迁移及线上回退 | P0 | Codex 事先验证备份和恢复。写入开放后优先保全实际数据，按发布手册决定恢复路径。 |
| 地图、模型、天气和航班不稳定或耗尽额度 | P1 | 使用已有缓存、限流和熔断，管理供应商调用预算。预案覆盖超时、缺数据和恢复后的验证。 |
| AI 行程有错误事实、价格或无来源内容 | P1 | 来源、估算和未知明确展示。人工抽查跨城路线、时间冲突、季节性和费用项。 |
| 改版使关键入口更难找到或页面变慢 | P1 | 先比对同环境基线。目标为 5 名试用者中至少 4 名能独立完成生成、保存和再次打开，同时记录首屏主要内容加载时间与操作耗时。 |

风险登记字段为 `风险 ID / 影响 / 概率 / 触发条件 / 等级 / 负责人 / 对应测试 / 截止时间 / 状态`。每轮由 Muse 在阶段检查时更新，Codex 在合并前和上线前复核。生产发布观察规划发起到完成率、取消率、恢复率、保存失败率、地图与供应商降级率、后端延迟及关键错误。使用已有指标和脱敏计数，先测基线并给当轮异常阈值。上线后按预设观察窗口在同一 Issue 记录验证结果。关键路径失败按 [发布与回退手册](../deploy/RELEASE_RUNBOOK.md) 执行。

## 6. 交接与下一轮

Codex 建立主任务卡并锁定提交。WorkBuddy 前端窗口交付首页和规划页的桌面、移动原型及可访问性验收图，后端窗口交付状态契约、可复现的离线基线及用例清单。两窗口共同确认地图、费用、保存位置和错误契约。Muse 对关键用例和风险登记做第一次评审。Codex 依据实际基线排序实现批次，终审通过且获授权后执行发布。
