# RAG 检索层说明（2026-11-26）

这份文档解释「行程生成前先查站内资料」是怎么做的、为什么这么做，以及它现在的能力边界。给两类读者：接手代码的人，和要在面试里讲清楚这个项目的人。

## 1. 一句话说清 RAG

RAG（Retrieval-Augmented Generation，检索增强生成）就是：模型答题前，先从自己的资料库里查出几段相关材料，连同问题一起塞进提示词。模型本身没变，变的是它答题时手里有材料，不用全凭记忆编。

在本项目里，用户说「成都 3 天，带 5 岁孩子，少走路」，系统先去知识库找出「成都·观光」里关于熊猫基地、人民公园的段落，把这几段附在用户需求后面，再让 GLM 排行程。行程页底部会列出参考了哪几篇资料，点得开原文。

## 2. 数据流

```
离线（灌库，只跑一次或换语料时跑）
  维基导游正文 / spots 表
        │  切块：400 字/块，重叠 80 字，按行和句号切
        │  向量化：智谱 embedding-3 → 1024 维 float32
        └─ 写入 knowledge_chunks（向量存 BLOB，4KB/条）

在线（每次规划）
  clarify 得到 collected
        │  query = preferences + party + pace（城市不进 query，走硬过滤）
        │  口语改写：带娃→亲子/儿童；不想爬山→平路/缆车/少台阶
        │  城市硬过滤 + 余弦相似度 + 关键词覆盖率 + 意图修正
        │  阈值 0.35 截断，取 Top-5
        └─ 注入 user message（SYSTEM_PROMPT 一字不动）
                │
                └─ 行程 JSON 带 references（id/标题/出处）→ 前端展示
```

编排图从四节点变成五节点：

```
clarify ──(done=True)──> retrieve ──> generate ──> verify ──> weather ──> END
   └──────(done=False)──> END
```

`retrieve` 失败只写一条「未匹配到站内资料」的日志，继续生成。和「天气失败不阻断」是同一套原则：增强项不能变成单点故障。

## 3. 为什么不引入向量数据库

数据量是 1708 条片段，一次查询只过滤出一个城市的 30-170 条，numpy 算余弦不到 2 毫秒。Chroma / Qdrant / Milvus 任何一个都要额外进程和 200-500MB 内存，而服务器只有 2G；还要多写 systemd 单元、健康检查、备份策略。收益是零，成本是实打实的。

同理没选 `sqlite-vec`（扩展在 Windows 开发机和 Linux 服务器上编译产物不同，部署风险高）和 `sentence-transformers`（torch 约 2GB，2G 内存的机器装完没有余量）。

什么时候该换：片段到十万级、或需要多租户隔离时，把 `knowledge.search()` 的实现换掉即可，调用方不用动。

## 4. 关键参数与理由

| 参数 | 取值 | 理由 |
|---|---|---|
| 切块大小 | 400 字 | 中文攻略一个景点介绍通常 100-300 字；400 字能容纳 1-3 个 listing，再大就会把无关景点混进来 |
| 重叠 | 80 字 | 防止一句话被切断；按句号边界取尾，不产生半句开头 |
| 向量维度 | 1024 | 智谱 embedding-3 支持 256/512/1024/2048；1024 在精度和 4KB/条的存储间平衡 |
| 城市过滤 | 硬过滤 | 目的地是确定信息，没必要让模型在向量空间里猜；同时把候选从 1708 条降到几十条 |
| 阈值 | 0.35 | 低于它的片段基本是「同城但无关」；0.30/0.35/0.40 三档 Recall 相同，取中间值留余量 |
| Top-K | 5 | 超过 5 条 token 成本上升，召回增益很小 |
| 混合权重 | 0.8 向量 + 0.2 关键词 | 中文 embedding 余弦多在 0.45-0.65，按 0.7/0.3 会把长偏好整体压到阈值以下 |

## 5. 三个容易被追问的设计点

**为什么 query 里不放城市？** 城市已经做了硬过滤，再放进向量里会让「成都」这个高频词主导相似度，把「带娃」「少走路」的权重压掉。

**为什么关键词只占 0.2？** 关键词分是为了捞专有名词（洪崖洞、漓江、游5路），不是主排序。权重再高会让「攻略正文里恰好出现这个词」压过语义相关但用词不同的段落。

**为什么要有意图修正？** 纯向量有个盲区：「少走路」在向量空间里离「公交/地铁」很近（少走路 = 坐车），但用户要的是「走路少的景点」，不是公交时刻表。所以用户没问交通时，交通章节降 0.05 分；问「室内/下雨」时，博物馆类加 0.04、户外类减 0.03。幅度都很小，只影响临界排序。

## 6. 语料与授权

- 维基导游正文：20 个城市，1208 个片段，CC BY-SA 4.0。每个片段存 `source_url`（指向 `oldid` 固定版本，内容不会被后续编辑改掉），前端展示出处时标注授权。
- 站内景点：500 条，来自高德 POI。线上库的 `description` 大量为空，所以片段文本由「名称 + 城市/区县 + 标签 + 地址」拼成。
- `guides` 表目前是空的。等站内有了真实攻略，`guides` 也可以接进同一个 `knowledge_chunks`（`source_type='guide'` 已被维基占用，站内攻略建议用 `source_type='ugc'` 区分）。

### 离线搬运（生产服务器用这条）

生产服务器在腾讯云，访问 `zh.wikivoyage.org` 会超时（2026-11-26 实测），不能直接跑 `ingest_guides.py`。做法是在本机灌好、导出、上传、导入：

```bash
# 本机（在 backend/ 下）
python scripts/export_knowledge.py --output ../knowledge-2026-11-26.jsonl

# 上传后，在服务器的新版本目录里
python scripts/import_knowledge.py --input /tmp/knowledge-2026-11-26.jsonl --dry-run
python scripts/import_knowledge.py --input /tmp/knowledge-2026-11-26.jsonl
```

导入会先清空 `knowledge_chunks` 再整批写入；条数、维度、base64 任何一项不符都会在动库前中止。景点片段用 `spots.id`，维基片段用 MediaWiki `pageid`，两台机器的 spots 数据同源（1=都江堰景区），所以 id 可以直接搬。

## 7. 指标（2026-11-26 实测）

| 指标 | 数值 |
|---|---|
| Recall@3 | 0.95（19/20） |
| 平均检索耗时 | 约 250 ms（多次实测 247-256 ms，含 embedding API；最慢约 510 ms） |
| 片段总数 | 1708（guide 1208 + spot 500） |
| 参数敏感性 | 阈值 0.30/0.35/0.40 × K 3/5/8 九组，Recall 全部 0.95 |

未命中那条是「丽江 古城 住宿」：丽江条目本身没有住宿章节，语料里没有答案，属于语料缺口而不是检索缺陷。

复现：`python scripts/eval_retrieval.py`（在 `backend/` 下）。评测集在 `tests/eval_queries.json`，用关键词判定而不是片段 id——灌库是整表重建，id 每次都会变。

## 8. 已知限制

1. **否定句仍然弱。** 「不想爬山」靠改写词典处理；没收录的说法（如「腿脚不便」）可能仍然召回登山线路。
2. **小城市语料薄。** 大理 25 个片段、丽江 11 个；这类城市检索到的内容有限。片段数少于 5 的城市可以考虑不接。
3. **切块会混入相邻景点。** 一段 400 字里可能有两三个 listing，模型引用时不一定能精确到某一个。
4. **没有 rerank。** 交叉编码器能再提 5-10 个点，但要多一个模型和 100-300ms；当前指标够用，先不加。
5. **行程生成偶发结构校验失败。** 模型偶尔把 `cost_category` 写成「购物」这类非法值，会触发重生成；这是既有校验的严格性，与 RAG 无关，但注入资料后 prompt 变长，发生概率会略升。

## 9. 面试口径（三分钟版）

> 这个项目要在生成行程前先查站内资料。我用智谱的 embedding-3 把维基导游和景点数据切成 400 字片段、向量化后存进 SQLite，不引独立向量库——数据只有一千多条，单机算余弦两毫秒，多一个服务的运维成本不划算。
>
> 检索时先按城市硬过滤，再算余弦，同时加 0.2 权重的关键词分捞专有名词，最后按意图做小幅修正，比如用户说「少走路」时压低公交章节。阈值 0.35，取前 5 条注入提示词，系统提示词一个字不改。
>
> 检索失败会降级成普通生成，不影响主流程。评测用 20 条自建查询算 Recall@3，现在 0.95，平均约 250 毫秒。
>
> 最大的坑是「少走路」在向量空间里接近「公交/地铁」，纯语义检索会返回公交时刻表；加了一个显式的意图判断才修好。这件事让我确认：RAG 的效果上限一半在语料和切块，一半在 query 改写，模型本身反而没那么关键。
