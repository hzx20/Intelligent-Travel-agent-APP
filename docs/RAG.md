# RAG 检索层说明（2026-11-26）

这份文档解释「行程生成前先查站内资料」是怎么做的、为什么这么做，以及它现在的能力边界。给两类读者：接手代码的人，和要在面试里讲清楚这个项目的人。

## 1. 一句话说清 RAG

RAG（Retrieval-Augmented Generation，检索增强生成）就是：模型答题前，先从自己的资料库里查出几段相关材料，连同问题一起塞进提示词。模型本身没变，变的是它答题时手里有材料，不用全凭记忆编。

在本项目里，用户说「成都 3 天，带 5 岁孩子，少走路」，系统先去知识库找出「成都·观光」里关于熊猫基地、人民公园的段落，把这几段附在用户需求后面，再让 GLM 排行程。行程页底部会列出参考了哪几篇资料，点得开原文。

## 2. 数据流

```
离线（灌库，只跑一次或换语料时跑）
  维基导游正文 / spots 表
        │  切块：400 字/块，重叠 80 字，按行和句号切
        │  向量化：智谱 embedding-3 → 1024 维 float32
        └─ 写入 knowledge_chunks（向量存 BLOB，4KB/条）

在线（每次规划）
  clarify 得到 collected
        │  query = preferences + party + pace（城市不进 query，走硬过滤）
        │  口语改写：带娃→亲子/儿童；不想爬山→平路/缆车/少台阶
        │  城市硬过滤 + 余弦相似度 + 关键词覆盖率 + 意图修正
        │  阈值 0.35 截断，取 Top-5
        └─ 注入 user message（SYSTEM_PROMPT 一字不动）
                │
                └─ 行程 JSON 带 references（id/标题/出处）→ 前端展示
```

编排图从四节点变成五节点：

```
clarify ──(done=True)──> retrieve ──> generate ──> verify ──> weather ──> END
   └──────(done=False)──> END
```

`retrieve` 失败只写一条「未匹配到站内资料」的日志，继续生成。和「天气失败不阻断」是同一套原则：增强项不能变成单点故障。

## 3. 为什么不引入向量数据库

数据量是 1708 条片段，一次查询只过滤出一个城市的 30-170 条，numpy 算余弦不到 2 毫秒。Chroma / Qdrant / Milvus 任何一个都要额外进程和 200-500MB 内存，而服务器只有 2G；还要多写 systemd 单元、健康检查、备份策略。收益是零，成本是实打实的。

同理没选 `sqlite-vec`（扩展在 Windows 开发机和 Linux 服务器上编译产物不同，部署风险高）和 `sentence-transformers`（torch 约 2GB，2G 内存的机器装完没有余量）。

什么时候该换：片段到十万级、或需要多租户隔离时，把 `knowledge.search()` 的实现换掉即可，调用方不用动。

## 4. 关键参数与理由

| 参数 | 取值 | 理由 |
|---|---|---|
| 切块大小 | 400 字 | 中文攻略一个景点介绍通常 100-300 字；400 字能容纳 1-3 个 listing，再大就会把无关景点混进来 |
| 重叠 | 80 字 | 防止一句话被切断；按句号边界取尾，不产生半句开头 |
| 向量维度 | 1024 | 智谱 embedding-3 支持 256/512/1024/2048；1024 在精度和 4KB/条的存储间平衡 |
| 城市过滤 | 硬过滤 | 目的地是确定信息，没必要让模型在向量空间里猜；同时把候选从 1708 条降到几十条 |
| 阈值 | 0.35 | 低于它的片段基本是「同城但无关」；0.30/0.35/0.40 三档 Recall 相同，取中间值留余量 |
| Top-K | 5 | 超过 5 条 token 成本上升，召回增益很小 |
| 混合权重 | 0.8 向量 + 0.2 关键词 | 中文 embedding 余弦多在 0.45-0.65，按 0.7/0.3 会把长偏好整体压到阈值以下 |

## 5. 几个容易被追问的设计点

**为什么 query 里不放城市？** 城市已经做了硬过滤，再放进向量里会让「成都」这个高频词主导相似度，把「带娃」「少走路」的权重压掉。

**为什么关键词只占 0.2？** 关键词分是为了捞专有名词（洪崖洞、漓江、游5路），不是主排序。权重再高会让「攻略正文里恰好出现这个词」压过语义相关但用词不同的段落。

**为什么要有意图修正？** 纯向量有个盲区：「少走路」在向量空间里离「公交/地铁」很近（少走路 = 坐车），但用户要的是「走路少的景点」，不是公交时刻表。所以用户没问交通时，交通章节降 0.05 分；问「室内/下雨」时，博物馆类加 0.04、户外类减 0.03。幅度都很小，只影响临界排序。

**引用怎么落到具体某一天？** 不让模型输出编号——`SYSTEM_PROMPT` 不能动，而且编号格式错一个就整份 JSON 校验失败。改成后端做确定性匹配（`services/citations.py`）：拿每个地点的名字去资料正文里找，命中就把 `[1][2]` 写到该地点和该天的 `ref_ids` 上。规则只有两条，都是为了压误报：

- 完整地名（去掉括号注释）可以直接做子串匹配，但「公园」「博物馆」这类通用词除外。
- 去掉「风景区/古镇/博物馆」等后缀后的核心词，必须至少 3 个字才允许匹配。「人民公园」去掉后缀只剩「人民」，拿它去正文里搜会把人民路、人民广场全捞进来。

匹配在地图核实前后各跑一次，核实改名或替换地点后以最终名字为准。函数幂等，重复调用先清后写。

## 6. 语料与授权

- 维基导游正文：20 个城市，1208 个片段，CC BY-SA 4.0。每个片段存 `source_url`（指向 `oldid` 固定版本，内容不会被后续编辑改掉），前端展示出处时标注授权。
- 站内景点：500 条，来自高德 POI。线上库的 `description` 大量为空，所以片段文本由「名称 + 城市/区县 + 标签 + 地址」拼成。
- `guides` 表目前是空的。等站内有了真实攻略，`guides` 也可以接进同一个 `knowledge_chunks`（`source_type='guide'` 已被维基占用，站内攻略建议用 `source_type='ugc'` 区分）。

### 事实时效性清洗

维基正文里有大量「门票 60 元」「人均 50 元左右」「更新日期：2019-05」这类断言。价格和营业时间是最容易过期、也最容易被模型当真写进行程的东西：模型看到「人均 60 元左右」会照抄，用户到店发现涨到 120，比不写更糟。

处理原则是**删数字、留结构**：`knowledge.strip_stale_facts()` 把「门票 60 元」变成「门票」，让模型知道这里有门票，但不敢写具体金额。区间价（300-500 元/晚）、`¥` 前缀、「更新日期」都覆盖，中文之间的残留空格会收掉。

**只在注入提示词时洗，不在入库时洗。** 这一点和直觉相反，是实测逼出来的：

| 做法 | 留出集 Recall@3 | 问题 |
|---|---|---|
| 入库时洗 | 0.75 | 数字在原文里占了不少语义分量，删掉后片段变短、切块边界移动；住宿章节（「XX客栈 ¥120」一行一个）受影响最大 |
| 只在注入时洗 | 0.82 | 库里留着旧价格，但用户和模型都看不到 |

库里的脏数据不影响产品：检索用它算相似度，注入前由 `itinerary._strip_stale()` 剥掉，送给模型的文本是干净的。清洗只删不写，不会把「60 元」改写成「价格待核实」，避免在正文里塞进模型没说过的话。

### 离线搬运（生产服务器用这条）

生产服务器在腾讯云，访问 `zh.wikivoyage.org` 会超时（2026-11-26 实测），不能直接跑 `ingest_guides.py`。做法是在本机灌好、导出、上传、导入：

```bash
# 本机（在 backend/ 下）
python scripts/export_knowledge.py --output ../knowledge-2026-11-26.jsonl

# 上传后，在服务器的新版本目录里
python scripts/import_knowledge.py --input /tmp/knowledge-2026-11-26.jsonl --dry-run
python scripts/import_knowledge.py --input /tmp/knowledge-2026-11-26.jsonl
```

导入会先清空 `knowledge_chunks` 再整批写入；条数、维度、base64 任何一项不符都会在动库前中止。景点片段用 `spots.id`，维基片段用 MediaWiki `pageid`，两台机器的 spots 数据同源（1=都江堰景区），所以 id 可以直接搬。

## 7. 指标（2026-11-27 实测）

| 指标 | 数值 |
|---|---|
| 开发集 Recall@3 | 0.95（19/20） |
| 留出集 Recall@3 | 0.82（49/60） |
| 平均检索耗时 | 约 240-270 ms（含 embedding API；网络抖动时单次可到 1 秒以上） |
| 片段总数 | 1708（guide 1208 + spot 500） |
| 参数敏感性 | 阈值 0.30/0.35/0.40 × K 3/5/8 九组，开发集 Recall 全部 0.95 |

两套集要分开看。开发集是我写同义词表、调权重时对着改过的，0.95 只能防回归，不能当成效果证明。留出集 60 条写完就没再按它调过参数，0.82 是更接近真实的估计。

留出集 11 条未命中的归因：

| 原因 | 条数 | 例子 |
|---|---|---|
| 语料缺口 | 9 | 「厦门吃海鲜」厦门条目没有餐饮章节；「深圳看海」观光章节没列大梅沙；「桂林象鼻山」正文只写了独秀峰、漓江峰丛 |
| 标注过严 | 1 | 「三亚哪个海滩」返回椰梦长廊、小东海，也是海滩，只是不在我列的三个里 |
| 切块 | 1 | 「成都火锅」火锅内容落在「用餐」章节的另一块 |

**没有一条是排序算法写错。** 这说明继续调权重、加 rerank、换向量库都不会有实质提升；能提分的只有补语料（景点描述 + 真实攻略）。这个结论比 0.95 那个数字有用。

另外记一笔失败的尝试：曾在入库时清洗价格（`strip_stale_facts`），留出集从 0.82 掉到 0.75。数字在原文里占语义分量，删掉后片段变短、切块边界移动，住宿章节（「XX客栈 ¥120」一行一个）受影响最大。最后改成只在注入提示词时清洗，向量仍基于原文。

复现：`python scripts/eval_retrieval.py`（开发集）、`--set holdout`（留出集），都在 `backend/` 下。评测集在 `tests/`，用关键词判定而不是片段 id——灌库是整表重建，id 每次都会变。

## 8. 行程密度：两层兜底

模型经常一天只排一两个点，剩下用「午餐 / 自由活动 / 返回酒店」占位。结构校验只要求每天至少一个地点，餐饮休息都算数，所以这种行程能过。

处理分两层：

1. **提示词**：每天 4-6 项、至少 3 个具名地点（餐饮交通休息不算），同一个远郊景点只排一天，每天地点尽量在同一片区域。
2. **补点**：生成后还有天不足 3 个，从同城 `spots` 表补到 3 个（每天最多补 2 个），写 `filled=True`，前端显示「补充推荐」。补位优先市区景点，县级市（都江堰市、彭州市）排最后——把都江堰补进「动物园 + 塔子山」那天，路线要横穿整个成都平原。

中间试过第三层「密度不足就重生成一次」，上线第一天就被打回来了：那次第一次生成密度不足，占用了第二次机会；第二次模型把费用类别写成「景点门票」，校验直接判失败，用户拿到的是「生成失败」。为了多一个景点牺牲整单成功率不划算，这条去掉了。

顺带把费用类别从「只认五个词」改成归一化：「景点门票」→ 门票、「市内交通」→ 交通、「购物」→ 其他，认不出来归「其他」。以前一个词的差异就让整份行程作废，这比少一个景点严重得多。

实测（成都 2 天亲子悠闲）：

| 版本 | 每天地点数 | 耗时 |
|---|---|---|
| 只有提示词 | 2 / 2 | 2m22s |
| 提示词 + 补点 | 3 / 3 | 1m28s |

## 9. 已知限制

1. **瓶颈是语料，不是算法。** 留出集 11 条失败里 9 条是语料里根本没有答案。`guides` 表 0 条，景点描述大量为空。继续调权重、加 rerank 的收益远小于补 20 个城市的景点介绍和真实攻略。
2. **否定句仍然弱。** 「不想爬山」靠改写词典处理；没收录的说法（如「腿脚不便」）可能仍然召回登山线路。留出集里「带老人去杭州，腿脚不方便」就没命中。
3. **引用靠名字匹配。** 资料里写「宽窄巷子」、行程里写「宽窄巷子景区」能对上；写「锦里古街」和「锦里」也能对上；但如果模型用了完全不同的别名（「蓉城」对「成都」），就标不上。宁可漏标，也不误标——误标会让用户点开一个无关链接。
4. **密度只有观测没有强制。** `itinerary.density` 记下每天有几个具名地点，不足时只写进日志，不触发重生成。改成硬约束会让真模型更容易整单失败，等有评测证明重试划算再改。
5. **小城市语料薄。** 大理 25 个片段、丽江 11 个；这类城市检索到的内容有限。
6. **没有 rerank。** 交叉编码器能再提 5-10 个点，但要多一个模型和 100-300ms；当前指标够用，先不加。

## 10. 面试口径（三分钟版）

> 这个项目要在生成行程前先查站内资料。我用智谱的 embedding-3 把维基导游和景点数据切成 400 字片段、向量化后存进 SQLite，不引独立向量库——数据只有一千多条，单机算余弦两毫秒，多一个服务的运维成本不划算。
>
> 检索时先按城市硬过滤，再算余弦，同时加 0.2 权重的关键词分捞专有名词，最后按意图做小幅修正，比如用户说「少走路」时压低公交章节。阈值 0.35，取前 5 条注入提示词，系统提示词一个字不改。
>
> 效果我做了两套评测：一套 20 条是调参时用的，0.95；另一套 60 条写完就没再动，0.82。留出集 11 条失败里有 9 条是语料本身没有那个内容，比如厦门条目没有餐饮章节。所以瓶颈在语料，不在排序——这也是我下一步不打算换向量库、不打算加 rerank 的原因。
>
> 引用我做成了确定性的：不让模型输出编号，而是拿行程里的地点名去资料正文里匹配，命中就把 [1][2] 标到那一天的安排上。因为系统提示词里是严格的 JSON schema，加一个字段就要改校验，格式错一次整份重生成，代价不划算。
>
> 还有一个反直觉的发现：我本来在入库时清洗价格，结果留出集从 0.82 掉到 0.75。数字在原文里占语义分量，删掉后切块边界移动，住宿章节受影响最大。最后改成只在注入时清洗，向量仍基于原文。
>
> 这件事让我确认：RAG 的效果上限一半在语料和切块，一半在 query 改写，模型本身反而没那么关键。
